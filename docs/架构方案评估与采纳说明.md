# 需求架构方案评估与采纳说明

评估对象：《配电网本体模型构建与知识推理》项目架构方案（Word 文档，共十节）。

评估目的：判断该方案哪些内容应当吸收进本项目，哪些不适合当前交付形态，并说明理由。

结论先行：**方案的技术骨架与本项目一致，可以互相印证；但它的技术选型偏生产级重型组件，
直接照搬会让演示部署变复杂，所以按"吸收能力、替换实现"的方式采纳。**

---

## 一、先判断这份文档的性质

文档开篇第一句是"结合甲方提供的《配电网本体模型构建与知识推理》需求，我建议把这个项目设计成一个完整的……"，
结尾又写"我尤其想确认一个事情：甲方希望交付的是一个能演示业务逻辑的原型，还是一个可以接入
电力公司真实数据、具备实际业务使用能力的系统？"

这两句话说明：**它是一份基于需求的架构建议稿，不是甲方下发的需求规格说明书。**
因此对它的正确态度是"评估采纳"，而不是"逐条实现"。也正因为如此，它最后那个问题
（原型还是生产系统）目前仍然悬空，这决定了后续工作量的量级差异，必须由甲方明确。

---

## 二、值得吸收的部分（已采纳）

### 1. 数据接入与治理作为独立模块

文档把"电力数据接入与治理"列为八大模块之首，并给了具体清单：文件导入、字段映射、
编号唯一性校验、关系完整性校验、缺失数据检查、重复设备检测、数据标准化、数据变更记录。

**这一条本项目原先缺失，现已补齐。** 原因是它决定了甲方第一个问题——"我们自己的台账能不能进来"。
如果只能演示预置数据，方案再漂亮也会在第一次对接会上被问住。

已实现：`app/ingest/` 四个模块 + 两张 CSV 模板 + 13 项字段映射 + 9 条校验规则（V1~V9）
+ 5 条拓扑规则（T1~T5）+ 三元组预览。
实测：37 行台账 + 15 条拓扑边 → 生成 176 条三元组 → 用生成的图重跑推理，
" S1 断开失电 1200 户""1 个可行转供方案"与原实例完全一致。

### 2. 明确"本体 / 知识图谱 / 推理引擎"三者分离

文档专门写了一段："本体模型定义电力设备是什么，知识图谱保存真实设备及其关系，
推理引擎根据设备关系、运行状态和业务规则得出结论。这三个模块不能混在一起。"

本项目一开始就是这样分层的：`ontology/grid-ontology.yaml`（概念）、
`data/grid-instances.yaml`（实例）、`app/reasoner/`（推理）。
这条判断是对的，也解释了为什么改本体能改变推理结果——代码里没有任何硬编码的电网结构。

### 3. 阈值必须可配置，且要注明"不是行业标准"

文档在过载规则那里主动加了一句："这里的 80% 是演示用阈值，不是甲方提供的电力行业标准，
实际阈值需要由甲方确认。" 这是文档里最诚实的一句话。

**已采纳并工程化**：阈值从代码里抽出来，放到 `data/thresholds.yaml`，
界面上可实时拖动滑块，改动立即影响过载判定与转供可行性，推理链里会写明"本次用的是哪个阈值"。
这样评审现场甲方说"我们按 90% 管"，改一个数就能演示，不用改代码。

### 4. SPARQL 查询能力

文档把 SPARQL 列为知识图谱模块的必备能力，并推荐 Apache Jena Fuseki 承担存储与查询。

**能力已采纳，实现替换**：不引入 Jena（见下一节），改用 rdflib 原生 SPARQL 引擎，
开放 `/api/sparql/query` 只读接口 + 8 条示例查询，界面可直接执行。
查询默认跑在 **OWL RL 闭包后的推理图**上（2465 条三元组，其中 1549 条是推导出来的），
所以甲方问"推理后的图长什么样"，可以直接查给他看。

安全边界做了四层：只允许 SELECT/ASK/CONSTRUCT/DESCRIBE；写操作关键字一律拒绝；
在图的副本上执行，改不到主图；行数上限 + 10 秒超时。

### 5. 操作日志与推理记录

文档第 8 模块列了：操作日志、推理记录、Agent 工具调用审计、本体版本管理、数据导入审计。

**已实现**：`app/audit.py` 把每一次问答、推理、SPARQL 查询、数据校验都落成 JSONL，
可按类型检索、可统计规则命中分布、可查最慢一次调用。
本体与实例数据的版本用 **内容 SHA256** 标识（不是人工版本号），
任何人改了 TTL，哈希就变，无法说谎。界面上"本体模型"页顶部那一条就是版本凭证。

### 6. "不要把推理交给大模型"这条底线

文档写得很重："电力业务涉及准确性，尤其是故障传播、负荷计算和转供可行性，
应该由确定性的程序和规则引擎负责。大模型负责理解问题和解释结果。"

本项目从第一版就守这条线：Agent 只做意图识别与工具选择，
**所有数字都来自推理引擎，答案里出现的每个数字都能在工具返回里找到出处**。
界面上右侧的"推理链"就是给甲方核对这件事用的。

## 三、不建议照搬的部分（已替换，附理由）

### 1. Apache Jena Fuseki + PostgreSQL + Redis + MinIO 全套

文档自己也说"不建议一开始同时上 Neo4j、Jena、Milvus 三套"，但推荐的方案里仍需
Jena（RDF 存储）+ PostgreSQL（业务库）+ Redis（缓存）+ MinIO（文件）四个中间件。

**不采纳，理由**：本项目是单机演示，四个中间件意味着甲方 IT 要先准备四套环境、
四个端口、四份账号。任何一套起不来，演示就卡在那里。
rdflib 在内存里加载 2465 条三元组、SPARQL 查询 24 毫秒返回，完全够演示与验收。
数据规模到十万级三元组、需要多人并发写入时，再换 Jena 是平滑的（SPARQL 语句不用改）。

### 2. Vue 3 + Element Plus + AntV G6 前端

**不采纳，理由**：这套组合需要 Node 构建链（`npm install` 常在甲方内网失败）。
本项目用原生 JS + ECharts 单文件，`python run.py` 就能跑，拷到任何一台机器双击 `start.bat` 即可。
演示稳定性优先于工程规范性——真到产品化阶段，前端重写是独立决策，不影响后端。

### 3. LangGraph 作为 Agent 编排框架

**不采纳，理由**：本项目的编排逻辑只有一件事——"LLM 决定调哪个工具 → 执行 → 结果回填 → 再问 LLM"，
用一个 135 行的类就够了，且每一步都能打日志、能断点。
引入 LangGraph 会把这条链路藏进框架抽象里，评审时反而不好解释。
如果甲方后续要做多 Agent 协作（比如"故障研判 Agent"+"工单调度 Agent"），再引入不迟。

### 4. 数据库设计里的 11 张表

**部分不采纳，理由**：文档列了 equipment、feeder、transformer、power_user、fault_record 等 11 张表。
但本项目的知识表示就是 RDF 图——设备、关系、属性都在 TTL 里，
再建 11 张关系表等于把同一份数据维护两遍，必然冲突（文档第六节自己也提醒了这个风险）。

**替代做法**：单一事实来源是 TTL；需要表格视图时用 SPARQL 查出来渲染。
界面上"运行审计"是唯一落盘的结构化记录（JSONL），因为它记录的是"发生过什么"，不属于知识。

### 5. 六个 Agent 工具

文档建议先做 6 个工具（query_equipment / query_topology / analyze_fault / analyze_overload /
evaluate_transfer / query_power_users）。

**已超出**：本项目 10 个工具，且按"业务问题"粒度切分而非"数据查询"粒度——
`simulate_switch`（开关动作后的失电范围）、`plan_transfer`（转供可行性）、
`transformer_relief`（配变过载怎么办）、`maintenance_scope`（检修停电推算）、
`fault_analysis`（故障—停电—工单闭环）等。
区别在于：`query_topology` 只返回拓扑数据，模型还得自己算；`simulate_switch` 直接给结论，
模型没有算错的机会。

## 六、仍然存在的差距（如甲方要求生产级）

以下内容本 Demo **没有做**，原因是它们只在生产环境有意义，做进演示会稀释重点。
如果甲方确认要往生产系统走，这些是第一批要补的：

1. **用户登录与权限**：角色（调度员/检修/查看）、数据权限、操作二次确认。
   文档第 8 模块明确要求，且电力公司验收通常必查。
2. **真实数据接入**：目前支持 CSV；生产要对接配电自动化系统（DMS）、用电信息采集系统、
   PMS2.0，涉及接口协议、实时流、数据质量 SLA。
3. **专业校核**：转供结论目前只做容量与拓扑校验，**未做**保护定值、相序、短路电流、
   电压降落、并列运行限制校核。文档第 4.3 节也明确说这些只能给候选方案。
   这一点必须在验收时讲清楚，否则会被理解成系统能给调度指令。
4. **图数据库替代**：数据量到十万级三元组、需要多人并发时，按第三节的说明切换 Jena。
5. **部署形态**：Docker Compose / 内网离线安装包 / 等保测评相关配置。
6. **功率因数与单位**：当前容量与负荷统一按 kW 处理，真实台账多为 kVA，需引入功率因数换算。

## 七、结论

这份文档的价值在于**业务判断**：它正确识别了本体、图谱、推理引擎三者的关系，
正确指出了"不能把推理交给大模型"，也诚实地标注了阈值需要甲方确认。
这些判断本项目全部采纳。

它的不足在于**技术选型偏重**：四个中间件、前端构建链、Agent 框架、11 张关系表，
对演示环境是负担而非优势。本项目用等价能力替换了实现，保持"一条命令跑起来"。

**下一步需要甲方明确一件事**：交付目标是"能演示业务逻辑的原型"，还是
"可接入真实数据、具备实际业务使用能力的系统"。这个问题的答案会让工作量相差数倍，
也决定了上面第六节那六项要不要启动。

在此之前，本系统作为演示与方案验证的载体已经完整可用：
本体可改、数据可进、图可查、推理可核、结论可追溯。
