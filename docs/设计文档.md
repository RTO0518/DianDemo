# 配电网本体模型设计说明

## 一、本体不是数据库

数据库回答"是什么"，本体回答"所以呢"。库表能如实记下"配变 A 挂在馈线 X""S1 在 A 的上游"，但当问题变成"若 S1 断开，哪些用户失电"，它只能把相关行都捞出来，剩下的推理压在使用者脑子里。本体不同：它把"上游开关断开则下游失电"写成规则，把开关状态当事实输入，结论便能被推出——S1 分位，LS2、LS3 不可达，配变 A/B/C 失电，三个台区共 1200 户受影响。这条链路由机器走完，且每一步都可回溯。

更本质的差别在约束。数据库的约束是列类型、外键、非空，防的是脏数据；本体的约束是逻辑公理，防的是自相矛盾的结论。"台区恰好一台配变"在库里只是两行记录，在本体里是一条基数公理，它直接推出"配变过载时台区内没有第二台配变可切"。所以当我们回答"配变 B 过载该切到哪条备用线路"，结论是无线路可切，只能切负荷 20 kW——这个"没有"是推出来的，不是查出来的。

## 二、设计取舍

其一，类名对齐 IEC 61970 CIM，但只取 28 个类。配电网 CIM 有数百个类，全量搬进来会让演示淹没在术语里；裁剪到设备、区域、用户、事件、量测、状态六个分支，保留主干语义，也留出与真实模型对接的口子。

其二，双层推理而非纯 OWL。OWL 的开放世界假设适合表达结构知识：上下游传递、基数约束、类不相交。但它不做数值比较、不做求和，也不默认"未声明即正常"。若强行用 SWRL 补齐，规则调试成本会超过收益。因此推理被切成两层：结构层交给 OWL（16 条公理），行为层交给规则引擎（12 条规则），结论互相校验——规则层把"失电"断言回本体，由不相交公理检查同一台设备会不会既带电又失电。

其三，开关状态用个体而非字符串。OpenState、ClosedState 作为 OperatingState 的个体，开关只需一条 hasOperatingState 断言，"常态分位"与"当前状态"便可分开表达。转供方案的本质是打破常态分位的有意操作，这一点只有分层表达才说得清。

其四，拓扑只存一份。代码里没有任何硬编码的电网结构，拓扑、负荷、户数全部来自本体文件。改本体即改结论，这是本体系统该有的承诺。

## 三、本体如何支持推理

以"断开 S1"为例。R1 从变电站出发沿闭合开关搜索，得到带电集合；R2 取补集得失电设备；R3 经 hasTransformer 映射到台区并累加户数；R5 找到一端带电、一端失电的联络开关 L1，模拟合闸后重算，校验 F02 线备用 3200 kW 是否覆盖 1000 kW 转移负荷；R6 输出方案并按转供后负载率排序；R12 复核合闸后失电户数为 0。

同一套规则也解释了反例：若 F02 线晚高峰负荷升到 3400 kW，备用只剩 600 kW，缺口 400 kW，方案当场判为不可行。结论随事实改变，而不是随人改变。

这正是数据库给不了的东西：不是一堆相关的行，而是一条可复核的推理链。
